فئتان من المستخدمين

سرّ التوسّع هو الفصل بين مَن يدير النظام ومَن يستهلكه. المستخدمون المجتمعيون يتصلون بـ Supabase مباشرةً (محميّين بـ RLS) فلا يمرّون عبر خادمك.

الموظفون / المندوبون user_type = staff

  • مدير (admin) — صلاحيات كاملة
  • مشرف (supervisor) — إدارة وإشراف
  • مندوب (delegate) — يدير مشتركي مناطقه
  • ≈ 1000 مندوب · يعملون عبر خادم Dart (service_role)

المستخدمون المجتمعيون user_type = community

  • طلبات المساعدة — مالية، سلة غذاء، علاج، حجز طبيب…
  • المسابقات والختمات — مشاركة، نقاط، جوائز
  • التبرعات والتفاعل مع منشورات الأعمال
  • 100,000+ · يتصلون بـ Supabase مباشرةً + RLS

العلاقة المحورية: مندوب ↔ مشترك

كل مشترك وكل عائلة مُسنَدان إلى مندوب واحد، مع جدول تاريخ للإسناد يتيح إعادة التوزيع والتدقيق.

🔗 تجميع الاتصالات

آلاف العملاء عبر Supavisor على المنفذ 6543 (Transaction) — لا اتصال Postgres مباشر لكل جهاز.

🗂️ التقسيم الشهري

activity_logs وnotifications مقسّمة بالشهر — فهارس صغيرة وأرشفة = حذف قسم.

🏆 لوحة صدارة فورية

مُشغّل يحدّث total_points لحظياً من دفتر النقاط؛ الاستعلام فهرس ORDER BY … DESC.

🔒 RLS بأداء عالٍ

كل السياسات تستخدم (select auth.uid()) لتُحسب مرّة لكل استعلام لا لكل صف.

🖼️ الوسائط في Storage

الصور والصوت خارج القاعدة تماماً؛ الجداول تحفظ المسار فقط — buckets عامة وخاصة بسياسات.

⚙️ نزاهة تحت الضغط

UNIQUE يمنع الانضمام المزدوج، وخصم المخزون ذرّي، والنقاط دفتر إضافة-فقط.

الهوية عبر Supabase Auth

كل الجداول تشير إلى public.profiles(id) وليس إلى auth.users مباشرة — فمصدر الهوية قابل للتبديل من مكان واحد. عند تسجيل مستخدم جديد يُنشأ ملفه تلقائياً عبر مُشغّل handle_new_user(). 
-- ترقية مستخدم إلى مندوب بعد تسجيله في Supabase Auth:
select public.make_staff('mandoub1@charity.org', 'delegate', 'بغداد', array['الكرخ']);
⚠️ توصية أمنية: الباك-إند الحالي يستخدم _simpleHash وتوكنات في الذاكرة (غير آمنة). مع Supabase يمكن الاستغناء عنها واعتماد Supabase Auth (بريد/هاتف/OTP/Google) — وهذا يحلّ أيضاً مشاكل البريد وОТP السابقة.
